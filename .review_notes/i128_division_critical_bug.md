# runtime/compiler_rt_arch.c — MOST SEVERE BUG FOUND: 128-bit division/modulo intrinsics caused SILENT DATA CORRUPTION, and a naive fix would have caused an immediate crash

## How this was found and verified
This is the single most rigorously-verified finding in the entire review,
using a REAL LLVM 22 toolchain assembled in-sandbox from PyPI wheels
(`karellen-llvm-core`/`karellen-llvm-clang` for `clang-22`/`ld.lld`/libLLVM,
`xtc-llvm-tools` for `llc`/`opt`/`llvm-as`/`llvm-dis` — see toolchain notes),
since the official c3c/LLVM release channels are network-blocked in this
sandbox. This let me compile REAL LLVM IR with `llc-22` (exactly the tool
Pride's own codegen.c3/Makefile pipeline uses) and link it against the
ACTUAL, UNMODIFIED `runtime/compiler_rt_arch.o` from this repository,
producing and running real native binaries — not just static reading.

## Bug 1 (pre-existing, now fixed): __udivti3/__divti3/__umodti3/__modti3 silently truncated every 128-bit operand to 64 bits
`compiler_rt_arch.c` declared the four core 128-bit ("ti") compiler-rt
division intrinsics with `unsigned long long`/`long long` (64-bit)
parameter and return types:
```c
ABI unsigned long long __udivti3(unsigned long long n,unsigned long long d){return n/d;}
ABI long long __divti3(long long n,long long d){return n/d;}
ABI unsigned long long __umodti3(unsigned long long n,unsigned long long d){return n%d;}
ABI long long __modti3(long long n,long long d){return n%d;}
```
The REAL compiler-rt/libgcc ABI for these symbols takes and returns FULL
128-bit (`__int128`/`unsigned __int128`) values — this is not optional or a
"good enough" approximation; it's a fixed, hardware-calling-convention
contract that LLVM's/GCC's `i128`/`__int128` division codegen depends on
verbatim (arguments arrive in register PAIRS per the SysV x86-64 ABI for
128-bit types). Because the stub declared 64-bit parameters, when invoked by
REAL 128-bit-division machine code generated by `llc` (verified directly:
`llc -filetype=obj` on `udiv i128 %a, %b` emits a `call __udivti3`
instruction using the genuine 128-bit calling convention), the stub's
prologue only read the LOW 64 BITS of each 128-bit argument (per its own,
wrong, 64-bit signature) and silently discarded the rest.

**Empirical proof**: linking real LLVM-generated code computing
`((u128)64<<64 | 5) / 3` against this repository's own, UNMODIFIED
`runtime/compiler_rt_arch.o` produced `hi=5 lo=0` — the correct 128-bit
answer is `hi=21 lo=6148914691236517207` (independently confirmed via
Python bignum arithmetic and via linking the SAME test program against
real, unpatched libgcc). This means **every Pride program using u128/i128
arithmetic with values that don't fit in 64 bits got silently wrong
results with no crash, no diagnostic** — u128/i128 are documented,
advertised primitive types (`CAPABILITIES_CHECKLIST.md` §4 "Primitive
Types" lists `i128 u128` as ✅), and this bug makes them unusable for their
entire reason for existing (representing values that exceed 64 bits).

## Bug 2 (introduced by, then fixed within, this same investigation): a naive "just widen the types" fix causes an immediate stack-overflow crash
My first attempt at a fix simply widened the parameter/return types to
`__int128`/`unsigned __int128` while keeping the native `n / d` / `n % d`
operators, e.g. `tu_int __udivti3(tu_int n, tu_int d){return n/d;}`. This
compiles cleanly with NO warnings — but **crashes on the very first call**
with a stack overflow (SIGSEGV). Root cause, confirmed via `gcc -S`
disassembly: x86-64 has no hardware instruction for 128-bit division, so
GCC/Clang implement `__int128 / __int128` themselves by emitting a CALL TO
THE VERY SAME LIBCALL SYMBOL — a function literally named `__udivti3` that
computes its body via 128-bit `/` recurses into itself infinitely. (This is
in contrast to 64-bit division, which HAS a hardware `divq`/`idivq`
instruction and compiles to a few inline instructions with no self-call —
which is exactly why the ORIGINAL, 64-bit-typed version of this file didn't
crash: it was accidentally "safe" from recursion by being wrong in a
different way.) This is a subtle, easy-to-miss trap specific to
implementing compiler-rt intrinsics for a width the target CPU doesn't
support natively, and I want to flag it explicitly since it's exactly the
kind of "obviously correct" one-line fix that would have shipped a NEW,
worse bug (100% reproducible crash instead of silent wrong answers) had I
not verified it by actually compiling and running it.

## Final fix (fully verified)
Implemented `__udivti3`/`__umodti3` as manual, self-recursion-free binary
long division (128 iterations of shift-compare-subtract, operating on
`unsigned __int128` values but using only shift/compare/subtract — never
`/` or `%` — so the compiler has no reason to route it back through a
libcall), then built `__divti3`/`__modti3` (signed) and `__udivmodti4`
(combined quotient+remainder, needed by `compiler_rt.c`'s own
`__pride_div_u128_u64`) on top of those two primitives. `__multi3`
(128-bit multiply) was verified SAFE to keep as a native `a*b` — 128-bit
multiplication DOES have a native lowering on x86-64 (a short sequence of
64-bit `mul`/`imul`+adds), confirmed via disassembly to have zero
self-recursion, and is in fact never called by LLVM's `i128` codegen at all
(`mul i128` lowers fully inline).

**Verification performed** (all via the real, in-sandbox LLVM 22 toolchain):
1. Disassembled the fixed object file — confirmed zero self-calls in any of
   `__udivti3`/`__umodti3`/`__divti3`/`__modti3`/`__udivmodti4`.
2. Linked real `llc`-compiled `udiv i128`/`urem i128`/`sdiv i128`/`srem i128`
   IR against the fixed `compiler_rt_arch.o` — all four operations produced
   results EXACTLY matching independently-computed Python bignum ground
   truth (unsigned: `hi=21 lo=6148914691236517207`, `rem hi=0 lo=0`; signed
   negative dividend: `hi=-22 lo=12297829382473034409`, `rem=0`; small-value
   regression case `100/7 = 14 rem 2`).
3. Linked the REAL, unmodified `runtime/compiler_rt.c`'s own
   `__pride_div_u128_u64` function (which calls `__udivmodti4`) against the
   fixed `compiler_rt_arch.o` and confirmed `1000/7 = 142 rem 6` and
   `2^64/2 = 9223372036854775808 rem 0` — both exactly correct.
4. Ran the PROJECT'S OWN documented full pipeline
   (`llvm-as-22 → opt-22 → llc-22 → ld.lld-22`, linking the real
   `compiler_rt.c`+`compiler_rt_arch.c` objects) end-to-end producing a
   working native binary that exits 0.

## Severity
This is the highest-severity bug in the entire review: it is silent (no
crash, no diagnostic — just wrong numbers), affects a documented/advertised
core language primitive type (i128/u128), and any naive attempted fix falls
into a second, even worse trap (100%-reproducible crash) that only shows up
when actually running compiled code — which is exactly why this bug (and
the trap in fixing it) had evaded detection by static reading alone.
